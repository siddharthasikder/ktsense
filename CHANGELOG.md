# Changelog

## Unreleased

### Added

- `trace` and `context` take `--path <prefix>` and `--tests`/`--no-tests`, the same filters `grep` takes, to narrow their callers, test callers, usages, text references (Kotlin and Java) and annotated sites to one scope; the definition and implementors are never filtered. `--path` is a workspace-relative prefix matched with `starts_with`, repeatable and OR-combined; `--tests` keeps test sources and `--no-tests` production, by the KT-91 source-set rule, and the two together are a usage error (exit 2). Each filtered heading states the filter and the count it left out, as in `## Callers (3 under src/main; 31 others)` and `## Usages (37 sites in 4 files under ktor-server/ktor-server-core/; 5 others)`. Without a filter the output is byte-identical to before. JSON carries a `filter` object (the path prefixes, the test scope, and the per-section omitted counts), skipped when no filter was applied. The `trace_kotlin_symbol` and `explain_kotlin_symbol` MCP tools gain `path` (array) and `tests` (optional bool). The routed `trace` and `context` requests carry the filter, so the daemon protocol version is now 11 (KT-127).

- The routing guidance an agent reads (the README table, `contrib/agent-skill/SKILL.md`, and the MCP server instructions) now maps each question type to the command that answered it in a replay of 107 recorded agent questions: several terms or call sites to `grep` with `--path`, one branch of a body to `context --match`, callers and subtypes to `trace Type.member`, files of a kind to `map --compact --path`, partial names to `symbols --contains`, and a single known literal to a plain text search (KT-124).
- `ktsense grep` now searches `.java` sources alongside `.kt`/`.kts` under `--root`: each Java hit is attributed to its enclosing `Type.method` by the KT-114 pure brace-and-signature scan and classified as code, comment or string by the KT-112 Java lexer, and its file header is labelled `(production, java)` or `(test, java)`. `--kotlin-only` restores the earlier Kotlin-only scope, and an all-Kotlin root is byte-identical with or without it. `grep` also takes the rg flags agent sessions reach for by habit: `-w`/`--word` bounds the pattern with ripgrep's half word boundaries `\b{start-half}(?:...)\b{end-half}` (what `rg -w` uses, so a pattern with a non-word edge such as `->` counts the lines `rg -w` counts), `-i`/`--ignore-case` prepends `(?i)`, and `-F`/`--fixed-strings` runs it through `regex::escape`; they compose, and the hit count still equals `rg -c` with the same flags over `-g '*.{kt,kts,java}'`. A pattern beginning with `-` stays a pattern beside the new short flags, whether written `grep -w -- '->'` or `grep '-x'`. The `search_kotlin_text` MCP tool keeps its name for compatibility and gains `kotlin_only`, `word`, `ignore_case` and `fixed_strings`; its description states it covers Java. `grep` is not routed through the daemon, so the daemon protocol is unchanged (KT-122).

- A definition `trace` or `context` resolves to a `.java` file now fences its signature as ```` ```java ```` rather than ```` ```kotlin ````, in Markdown only (JSON is unchanged), so a Java signature is highlighted as Java. A Java text reference that falls on a multi-line method header, where the parameter list spans lines and the opening brace is on a later line, is now attributed to the method it opens rather than to its enclosing type: the KT-114 enclosing scan begins a named declaration's span at its header line. On a mixed Java and Kotlin service, `trace executePartialChange` fences the Java definition as Java and lists the line-61 header site under `UpdateDocumentBase.executePartialChange` (KT-126).
- A daemon started on first use in the background now idles out after fifteen minutes, while one started with `daemon start` keeps the hour-long default; `daemon start --idle <minutes>` sets either, and both paths pass the window to the detached `daemon serve` as a hidden `--idle` flag, where `KTSENSE_DAEMON_IDLE_SECS` still overrides it for tests. `daemon status` now shows `idle limit: N min`, read from the daemon's own status snapshot, so the window a running daemon holds is visible. The snapshot gained the field, so the daemon protocol version is now 10; a version-9 daemon left by an older build returns a snapshot without it and is reported as a mismatch rather than read short (KT-125).
- When `trace` resolves to a Java class or interface, its `## Implementors` section now lists the types that name it in a supertype clause: `extends`/`implements` in `.java` sources (scanned with the KT-114 lexer so a mention in a comment or string never matches, with generic arguments `Foo<Bar>` and qualified names `a.b.Foo` reduced to the simple name) and `:` supertype lists in `.kt` sources (the simple name of each existing Kotlin supertype). Each row carries the subtype's package-qualified name (KT-117 for Java, the skeleton for Kotlin) and `path:line`, under `precision: text match (supertypes matched by name)`. Direct subtypes come first; a subtype reached through another is listed after and marked `via <parent simple name>`, found by a bounded, cycle-safe fixpoint (depth cap 8). A Kotlin-declared type's implementors are unchanged, and JSON carries the list under `supertype_implementors` with a `via` field skipped for a direct subtype. The routed daemon reply is rendered text, so no protocol bump (KT-116).
- When `trace` or `context` finds no declaration for a name and the workspace under `--root` holds `.java` sources, the not-found answer now lists where the name appears in them as text, in a `## Java text references (N sites in M files)` section after the Kotlin `## Text references`, each Java site attributed to its enclosing method in the KT-114 grep layout (`Type.method`, trimmed source line) with comment and string mentions counted apart, and the not-found wording gains a sentence that Java-only names and generated accessors (Lombok, AutoValue, Immutables) appear there. A root with no `.java` file is byte-identical to before, in Markdown and JSON; JSON gains `java_text_references`, skipped when empty. The Java scan reuses the KT-112/KT-114 code, and the daemon renders the section into the answer text it already returns, so the routed request and reply shapes are unchanged and the daemon protocol stays 8 (KT-115).

- `map --path <substring>` (and the `path` argument of the `get_kotlin_repo_map` MCP tool) maps only
  files whose workspace-relative path contains the substring. The flag is repeatable and a file is
  kept if it matches any of them (OR), and it composes with `--compact`, `--focus` and `--fill`. The
  header states `Path filter <s>: K of N files`, naming how many of the mapped files the filter kept,
  and every downstream count (ranking, budget, omitted directories) is over the kept files alone. The
  filter is applied in `ktsense-core`, so JSON carries a `path_filter` object (substrings and the
  kept and total counts), skipped when no filter was given so an unrestricted map is byte-identical.
  The routed daemon request gained the filter, so the daemon protocol version is now 9. The MCP tool
  passes each path value as its own `--path` flag (KT-120).
- `map --compact --focus <regex>` now renders the Focus section and stops: the header reads `Focus only: N declarations in M files; K other files not mapped, pass --fill to map them`, naming how many other files carrying public declarations the focus did not reach, so a question that names a kind of declaration is answered without the rest of the budget spent on files it did not ask about. `--fill` (which requires `--focus`) spends what budget the focus section leaves on the ranked map, restoring the earlier focus behaviour byte-identically in Markdown. The default map and `--compact` without `--focus` are unchanged. JSON carries `fill` and, in focus-only mode, `other_files_not_mapped`; a map built with the ranked map still present serializes its files as before. The `get_kotlin_repo_map` MCP tool gains a `fill` argument. The routed daemon request shape gained the flag, so the daemon protocol version is now 8 (KT-110).
- When the workspace under `--root` holds `.java` sources, `trace` and `context` now report where the queried name appears in them as text, since the engine resolves Kotlin only. A resolved answer gains a `## Java text references (N sites in M files)` section (word-bounded scan, comment and string mentions counted apart through a pure Java lexer in `ktsense-core`), and its Callers heading reads `## Callers (N from Kotlin)` so a count the engine can give only for Kotlin is never read as the absence of callers. When the definition itself is in a `.java` file the Kotlin sources are text-scanned too, listed under `## Kotlin text references` with each hit attributed to its enclosing declaration (the KT-102 attribution), and the answer carries the note `References from Java sources are text matches; the engine resolves Kotlin only.` `context` carries the same sections in its budget after the callers, gated by the callers section. JSON gains `java_text_references` and `kotlin_text_references`, skipped when empty so an all-Kotlin workspace is byte-identical. The routed daemon reply is unchanged (rendered text plus exit), so no protocol bump (KT-112).
- `map --compact --focus <regex>` (and the `focus` argument of the `get_kotlin_repo_map` MCP tool) lists every public top-level declaration whose name matches the pattern first, grouped by file in the map's own rank order, before the ranked map spends what budget remains, so a question that names a kind of declaration is answered even when the ranking would have spent the budget elsewhere. `--focus` requires `--compact` and is rejected otherwise with a usage error, as is an invalid pattern. The MCP `focus` argument implies compact. JSON carries the matches under `focus`; a map without `--focus` is byte-identical to before, in Markdown and JSON. The routed daemon request shape gained the pattern, so the daemon protocol version is now 7 (KT-108).
- When `trace` resolves a name to an annotation class, or finds no declaration but the name is written as `@Name` in the workspace, the answer gains an `## Annotated (N)` section listing each declaration the annotation is written on by fully-qualified name, kind and file:line, grouped by file, from a tree-sitter pass over the sources. In the not-found case it sits between the KT-87/KT-104 not-found wording and the KT-94 `## Text references` section; the exit stays 1 when not found and 0 when resolved. The section states `precision: syntax (matched by name)`, because the annotation target is a parse fact while the annotation's identity is matched by simple name only. `context` carries the same section in its budget after the callers. JSON gains `annotated`, skipped when empty so an answer that lists no annotated declaration is byte-identical. The routed daemon reply is unchanged (rendered text plus exit), so no protocol bump (KT-109). Under `context --only`, the annotated declarations belong to the `callers` section.
- `map --compact` (and the `compact` argument of the `get_kotlin_repo_map` MCP tool) lists each mapped file's public declarations as kind and name only, with no signatures, supertypes or KDoc, so the same token budget covers far more of a module. On `ktor-server/ktor-server-core` at `--budget 4000` it surfaces 130 of the module's 136 public top-level types, against 40 for the default map. The default map is byte-identical to before. The routed daemon request shape gained the flag, so the daemon protocol version is now 6 (KT-97).
- `context --only <section>[,<section>...]` (and the `only` argument of the `explain_kotlin_symbol` MCP tool) renders the declaration line plus only the named sections, out of `source`, `callers`, `implementors` and `outline`, and spends the token budget on them alone. The full bundle is the default and is byte-identical to before, in Markdown and JSON; a filtered bundle carries a `sections` object in its JSON. The routed daemon request shape gained the filter, so the daemon protocol version is now 4 (KT-96).
- `context --match <regex> [--around N]` (and the `match` and `around` arguments of the `explain_kotlin_symbol` MCP tool) keeps the declaration line and, in the Source section, only the lines matching the pattern plus `--around N` context lines (default 1), each with its line number and `...` where lines were skipped. It composes with `--only`. Without `--match` the output is unchanged. The routed daemon request gained the pattern, so the daemon protocol version is now 5 (KT-101).
- Declaration lookups now read generated Kotlin under a module's `build/generated` and `build/generated-src` (covering KSP's `build/generated/ksp` and kapt's `build/generated/source/kapt`), which the engine does not index, and label those rows `generated`. `symbols --contains` reads them directly; an exact `symbols <name>` the engine answers with nothing falls back to the workspace's own syntax index, which does, stating `source: syntax index`. JSON carries `"generated": true` only on a generated row, so an ordinary answer is byte-identical. `map` and `outline` keep their build-free view. When a declaration lookup finds nothing, the not-found answer now says whether generated sources were searched or are absent and the build should be run (KT-104).
- The first `trace` or `context` in a root, finding no live daemon, now answers in process and then starts the warm daemon in the background, so the next question in the session is answered warm (about 50 ms against 0.7 to 2 s). The first answer is byte-identical to before and the background start never blocks or fails the command; concurrent first uses settle on a single daemon through the same flock claim `daemon start` holds. `KTSENSE_NO_AUTOSTART=1` answers in process without starting one, and `KTSENSE_NO_DAEMON=1` continues to skip routing entirely (KT-105).
- `ktsense grep <regex>` searches the workspace's Kotlin sources for a regular expression and groups each hit under its file and the declaration it falls inside, labelled production or test (the KT-91 source-set rule) and code, comment or string (the KT-83 classification). `--path` restricts to a subtree, `--tests`/`--no-tests` to one source-set kind, and `--limit` caps the hits shown per file. The answer states `precision: text match` so it is never read as a resolved reference, and the hit count equals `rg -c` for the same pattern; a hit line is `  <line>: <trimmed source line>`, trimmed to 160 characters. It needs no engine. The `search_kotlin_text` MCP tool exposes it, and the grouping and rendering are pure in `ktsense-core` (KT-102).

### Changed

- `symbols --contains` and the exact `symbols` syntax-index fallback now list a class's primary-constructor `val`/`var` properties as `val`/`var` rows named `<Class FQN>.<prop>`, so a partial-name search finds them even though the model carries a primary-constructor property as a parameter rather than a child. `symbols --contains CustomerId` now finds `qualificationCustomerId`, and on the fixture `--contains customerEmail` finds `shop.order.Order.customerEmail`. Class-body properties were already indexed and are listed the same way. Each row carries the property's declared type and visibility in its signature and is positioned on its class's line, since the model records no per-parameter line; the KT-88 ranking is unchanged, so an exact-name property outranks a longer containing one. `outline` and `map` are unchanged, and no snapshot moved (KT-123).
- An extension function or property is now indexed and found under its own simple name, with the receiver shown in the signature and kept out of the qualified name. The syntax adapter carries the receiver in a new `Declaration.receiver` field instead of baking it into the name, so `symbols blankToNull` resolves `internal fun String?.blankToNull()` to `...probe.blankToNull` (the exact lookup said no declaration before, and `--contains` reported `...probe.String?.blankToNull`), while the rendered signature still reads `fun String?.blankToNull()`. The fix reaches `symbols` (the exact syntax-index fallback and `--contains`), `trace`/`context` enrichment, `outline` and `map` alike. The default Markdown outline and every rendered signature are byte-identical; JSON outline carries the simple `name` plus a `receiver` field for an extension, so an extension row changed and a non-extension row did not. No routed daemon shape changed, so the protocol version is unchanged (KT-121).

- A `symbols` candidate the engine reports from a `.java` file now shows its real kind (`class`, `interface`, `enum`, `record`, `@interface`, `method`, `constructor` or `field`), its package-qualified name through its enclosing types, and its signature line, in place of the bare `name  symbol  path:line` row it printed before. A pure brace-and-signature scan of the Java file in `ktsense-core` reads the declaration at the engine's name and line (reusing the KT-112 Java lexer and the KT-114 enclosing walk), and the package comes from the file's `package` line. A Java constructor sharing its class's simple name and file is folded into the class candidate, so a Java type is not ambiguous with its own constructor and `symbols UpdateDocumentBase` answers with one row. Kotlin candidates are byte-identical (KT-117).

- `--pick` now stands alone as the query on `symbols`, `trace` and `context`, and as the `pick`
  argument of the `find_kotlin_symbol`, `trace_kotlin_symbol` and `explain_kotlin_symbol` MCP tools:
  the positional name is optional when `--pick` is given, the lookup name is then the pick's last dot
  segment (`ktsense_core::last_segment`), and the whole pick filters the matches as before, so an
  ambiguity hint can be rerun as written. An invocation with neither the positional nor `--pick` is a
  clap usage error (exit 2). The MCP `query`/`symbol` arguments became optional, which is backwards
  compatible (a call that still sends them works unchanged); the `tools_list` golden is updated. The
  routed daemon request carries the derived name as before, so the protocol version is unchanged
  (KT-119).
- `context` (and the `explain_kotlin_symbol` MCP tool) now lists at most three test callers by default, followed by one line `N more test callers; trace <name> lists them all`, so the budget goes to the source, the file outline and the production callers first; production callers are never capped. `--only callers` lifts the cap and lists every test caller. The Callers heading still counts every caller, so a capped answer is not read as having fewer. JSON mirrors the Markdown: the callers array carries only the listed callers plus a `test_callers_omitted` count, left out when the cap dropped nothing, so an uncapped bundle is byte-identical. On `ProfileUpdater.dispatch` in a mixed Java and Kotlin service (15 test callers) this cut the answer from 5,951 to 3,211 bytes. The routed daemon reply is unchanged (rendered text plus exit), so no protocol bump (KT-118).
- `daemon stop` now stops a daemon of any protocol version, `daemon status` names both versions when a live daemon's protocol differs from this build's, and an engine-backed command's autostart stops a mismatched daemon and starts a current one through the same flock claim, so an upgrade never strands a root behind the daemon an older build left warm. The stop frame and the hello are version-independent and pinned to their exact wire bytes; a deployed protocol-7 daemon was measured to announce that hello and accept that stop. A matched `status` is byte-identical in Markdown and JSON, and no routed request or reply shape changed, so the daemon protocol version stays 8 (KT-113).

- Each site in a `trace` or `context` `## Java text references` section now reads like a KT-102 grep hit: `  <line>: <trimmed source line>` (trimmed to 160 characters) grouped under the `Type.method` enclosing it, or `Type` for a field initializer or class-level site and `(file header)` for an import or package line. The enclosing comes from a pure brace-and-signature scan of the Java file in `ktsense-core`, reusing the KT-112 Java lexer, that recognises class, interface, enum and record headers and method and constructor headers, keeps control blocks, lambdas, anonymous classes and static initializers under their enclosing method or type, and composes nested and inner types as `Outer.Inner.method`. The section stays under `precision: text match` with comment and string mentions counted apart, and `context` lists the same lines within its budget. JSON sites gain `enclosing` and `text`, skipped when empty so an all-Kotlin workspace is byte-identical. The routed daemon reply is unchanged (rendered text plus exit), so no protocol bump (KT-114).
- A `context` answer viewed through `--match` now renders the declaration as one `<fqn>  <path>:<line>` line directly under the title, in place of the `## Declaration` heading and its signature fence, so a matched answer costs that one location line plus the matched source. The matched Source lines, the KT-107 chrome trimming, and the `index: partial` warning are unchanged; a `context` without `--match` (including `--only` without `--match`) is byte-identical to before, and the JSON is unchanged because it already carries the definition. This is a rendered-text change, so the daemon protocol is not bumped and a routed `--match` answer stays byte-identical to the in-process one (KT-111).
- A `context` bundle narrowed by `--only` or viewed through `--match` now renders without the budget line, the `index: complete` line and the trailing resolution note, and a `grep` answering fewer than five hits now renders without its aggregate count line, so a one-fact answer stays close in size to the equivalent `rg -n`. A partial index still prints its warning, the declaration (its signature fence under `--only`, its `path:line` location under `--match`, KT-111) and the hits themselves stay, and a few-hit `grep` still states `precision: text match`. A full `context` bundle and a `grep` of five or more hits are byte-identical to before, and the JSON of both is unchanged (KT-107).
- `symbols` now lists an enum class's entries, or a data class's primary-constructor properties with their types, on one line under the row when a lookup resolves to exactly one declaration; a listing of several matches is unchanged. The JSON gains `entries` (an array of names) or `properties` (name and type objects), skipped when empty so a non-enum, non-data, or multi-candidate result stays byte-identical. The entries and properties are extracted by the tree-sitter adapter into the skeleton and rendered in `ktsense-core` (KT-103).
- `trace`, `context` and `symbols`, and the `symbol`/`query` arguments of the `trace_kotlin_symbol`, `explain_kotlin_symbol` and `find_kotlin_symbol` MCP tools, now accept a dotted `Type.member` argument such as `OrderRepository.save`. The last dot-separated segment is the declaration name the engine looks up, and the whole query then filters the matches as a dot-boundary suffix: a unique match answers directly, several exit 3 listing only those, and none keeps the not-found answer (whose text-reference search uses the last segment). An explicit `--pick` still wins over the dotted filter (KT-100).
- `--pick` on `symbols`, `trace` and `context`, and the `pick` argument of the `find_kotlin_symbol`, `trace_kotlin_symbol` and `explain_kotlin_symbol` MCP tools, now accepts a dot-boundary suffix of a fully-qualified name as well as a full FQN, such as `InMemoryOrderRepository.save` for `shop.db.InMemoryOrderRepository.save`. An exact FQN wins; a suffix matching one candidate selects it; a suffix matching several lists only those and exits 3; a suffix matching none keeps the pick-missed error. The ambiguity hint now names the shortest unique dot-boundary suffix of its example candidate rather than the whole FQN, so a rerun copies less (KT-95).

## 0.1.0

First stable release. It follows the `v0.0.1-rc.2` prerelease.

### Changed

- `context` (and the `explain_kotlin_symbol` MCP tool) now routes through the warm daemon, answering on the daemon's own session as a depth-1 `trace` instead of opening a fresh engine per call (KT-89).

### Fixed

- `symbols` now qualifies a class, object or function declared inside a function or property body. Such a local declaration was reported with no kind, package or enclosing chain because the file skeleton drops it with the body; the enrichment now falls back to a tree-sitter walk that finds it, so it carries its real kind, its package and a qualified name through its enclosing declarations (for example `io.ktor.server.application.ApplicationPluginTest.test_routing_scoped_install.Config`), is marked `(local)` in Markdown and `"local": true` in JSON, and is selectable with `--pick`. Top-level and member declarations are unchanged (KT-98).
- Signatures, supertypes and annotations lifted across several source lines now render on one line. The syntax adapter folds each such span through a pure `ktsense-core::text` normalizer that collapses whitespace runs, drops spaces just inside brackets and before commas, and drops a trailing comma before a closer, while leaving string literals and comments byte for byte so a default like `= "a  b"` and a multi-line raw string keep their contents (KT-92).

- `trace` and `context` no longer count comment, KDoc or string text, or a same-named declaration such as a `companion object`, as a caller. Each reference site is classified by the syntax node it falls in, only code uses become callers and usage rows, and the Usages line says how many text mentions and same-named declarations it left out (KT-83).
- A "no declaration named X" answer now says it searched this workspace only, not library dependencies (KT-87).
- `trace` and `context` no longer list a class as its own implementor (KT-77).
- A class that Kotlin makes final (not `open`, `abstract`, `sealed`, `enum` or `expect`) now reports no implementors. Before, same-named classes such as `FooTest` could be listed, because kmp-lsp 0.26.0 answers implementation requests on a final class with name matches. A partially parsed file keeps the engine's answer (KT-78).
- `symbols` candidates, including the ambiguous-name listing shared by `trace` and `context`, are printed in a stable order: qualified name, path, line (KT-81).
- The `trace` Usages heading now accounts for every site. When sites are left out by the per-file limit or as imports, the section says how many and why (KT-82).
- Concurrent `daemon start` calls decide who spawns with one atomic claim, so two starts can no longer both report success (KT-71).
- The MCP server instruction string names both version-guarded tools (KT-70).

### Added

- `trace` and `context` no longer end a name the workspace does not declare with a bare exit 1. After confirming no declaration resolves, the answer lists where the name appears as text in the workspace's Kotlin sources under `## Text references (N sites in M files)`, grouped by file, capped by `--limit`, and marked `precision: text match` so it is never read as resolved usages; comment and string mentions are listed but counted apart from code. The KT-87 scope wording stays and the exit stays 1, but the listing moves onto stdout so a routed daemon and the MCP tools carry the same answer. JSON carries the sites. This is what turns `putMetric`, `@RequestRouter` and generated `*RouterWrapper` names from nothing-to-act-on into the use sites a text search would have found (KT-94).

- `ktsense symbols --contains <query>` lists every declaration whose simple name contains the query, drawn from the workspace's own syntax index rather than the engine, so it needs no warm index and states `source: syntax index`. Matches are ranked exact name first, then prefix, then shorter name, then qualified name, path and line, capped by `--limit` (default 50) with a note when more were found; a query nothing contains exits with the workspace-scope wording. The `find_kotlin_symbol` MCP tool gains a `contains` flag (KT-88).

- `ktsense map` now says where its omitted files live. When files are dropped for budget, the Markdown map ends with an `Omitted: <dir> (<count>), ...` line grouping them by directory, most files first, truncated to `and N more directories` when the reserved room runs out; the summary's cost is reserved before files are chosen so the total stays within the budget. The map also states how many read files declare nothing public and were not mapped, and the JSON gains `omitted_directories` and `files_without_public_declarations` (KT-93).

- `trace` lists production callers under `## Callers` and test callers under a following `## Test callers`, at every `--depth` level, and `context` orders production callers ahead of test ones and labels the test ones, so who calls a symbol in production reads before who exercises it in tests. A caller counts as a test by its source path (a `test`, `androidTest`, `testFixtures`, `commonTest`, `jvmTest` or `<flavour>Test` source set, or a `Test.kt` / `Tests.kt` / `Spec.kt` file); JSON gains a `test` flag per caller (KT-91).
- `outline --annotations` shows each declaration's annotations, one per line above it; the default outline drops them and says how many it hid, and the `get_kotlin_outline` MCP tool gains an `annotations` argument (KT-90).
- `context` includes a `## Source` section with the declaration's own body, right after its signature. A body too long for the budget is cut on a line boundary with the omitted range to read (KT-86).
- On an ambiguous name, `trace` and `context` title the block `## Ambiguous: <name> (N candidates)` and print a `rerun with --pick <FQN>` hint on stdout and stderr, still exiting 3 (KT-85).
- `status` reports whether `rg` is on `PATH` and warns when it is missing, because engine `find` and references return nothing without it (KT-80).
- `outline` states how many private or internal declarations it hid and that `--private` includes them (KT-79).
- `scripts/install.sh`, a one-script installer. It asks before trusting the tap, installs ripgrep, and proves the install by running the binary (KT-75).
- README routing guidance on when ktsense's structured context helps and when literal grep is the better tool. The README makes no speed claim.

### Documentation

- The bundled engine's glibc floor (2.28) and the `KTSENSE_LSP_PATH` workaround are stated across all shipped docs (KT-72, KT-73).
- The Homebrew 7 tap trust step is documented (KT-74).

### Known limitations

- Resolution is syntactic, not type-checked. For an interface or open class, `Implementors` can still include a name-matched declaration from another package; supertype resolution is planned as KT-84.
- On Linux hosts below glibc 2.28 the bundled engine does not start. Set `KTSENSE_LSP_PATH` to a host-built `kmp-lsp` 0.26.0.
- In a like-for-like benchmark on ktor (KT-76), grep was faster on every question. ktsense's advantage is structured, smaller answers for questions such as callers of a nested type, not speed.
